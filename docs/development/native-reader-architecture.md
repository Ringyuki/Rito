# Native Reader Architecture

This document is a decision record and development plan for building a
production native reader on top of Rito. It deliberately treats Flutter as a
real product surface, not as a disposable integration.

UI design, interaction, motion, and app-shell implementation details are tracked
in [`native-reader-ui-plan.md`](./native-reader-ui-plan.md). This document owns
the runtime/session/frame architecture; the UI plan owns the immersive reader
experience built on top of that contract.

## Status

This is now a historical architecture record, not the active implementation
plan. The TypeScript `runtime/reader-session` and Web worker shell spike has
been removed from `@ritojs/core` because it was internal-only, unconsumed by the
stable Web reader, and insufficient for native render/font/image parity. The
active direction is a Rust core rewrite described in
[`native-core-rust-plan.md`](./native-core-rust-plan.md). Session, revision,
frame, and resource-transfer concepts below remain useful design inputs, but
the TS command shapes and file layout are no longer current source.

## Research Basis

The design below is based on three inputs:

- Current Rito boundaries: parser, style, layout, render, runtime, and
  interaction are already separated, but the native path currently mixes runtime
  state, diagnostics export, and UI input into one serialized book payload.
- Flutter platform constraints: expensive work must not run on the main isolate;
  worker isolates cannot mutate widgets or drive the render tree; platform
  channels can be called from registered background isolates; and frame work
  must fit the 16ms/8ms practical budget for 60Hz/120Hz targets.
- Reader architecture precedents: Readium separates publication parsing/resource
  access from navigator behavior, treats locators as source-based positions, and
  explicitly calls out pre-rendering nearby resources as a navigator concern.

## Decision

The production boundary is a long-lived reader runtime session, not a whole-book
serialized export.

Rito must expose a runtime contract that can open a publication, create layout
revisions, resolve source locators, and stream spread frames on demand. A
whole-book export remains useful for diagnostics and fixtures, but it is not the
main app contract and must not drive the Flutter reader.

The key unit consumed by Flutter is a `ReaderSpreadFrame`:

- one spread, already grouped by core
- one display list, already sized to the viewport
- all hit targets in spread coordinates
- all searchable text runs in spread coordinates
- resource references, not embedded full-book base64 payloads
- the revision id that produced it

Flutter paints and interacts with this frame. It does not regroup pages, infer
backgrounds, reverse-engineer links from paint commands, or keep page index as
the durable reading position.

## Decision Records

### DR-1: Runtime Boundary Is `ReaderSession`

Decision: the native reader talks to a long-lived `ReaderSession`, not a
serialized whole-book payload.

Rito evidence:

- `PaginationSession` is already stateful and incremental:
  [`PaginationSession`](../../packages/rito/src/reference/ts-core/runtime/pagination-session.ts#L38-L77).
- It keeps chapter, anchor, text index, and footnote maps:
  [`getResult`](../../packages/rito/src/reference/ts-core/runtime/pagination-session.ts#L208-L215).
- Runtime invariants already require platform-neutral runtime code:
  [`runtime is platform-neutral`](../../packages/rito/tests/unit/architecture-invariants.test.ts#L174-L183).

External evidence:

- Flutter documents long-lived isolates for repeated expensive work:
  https://docs.flutter.dev/perf/isolates.
- Flutter platform channels support registered background isolates:
  https://docs.flutter.dev/platform-integration/platform-channels.

Implementation rule: the production Flutter package must open a session, create
revisioned layouts, request frames on demand, and cancel stale work. Diagnostics
exports may exist, but they cannot be the runtime input format.

Acceptance:

- Opening a book does not require transferring every rendered page to Flutter.
- Resizing creates a new revision without discarding the active revision.
- Stale revision responses are rejected in tests.

### DR-2: Render Payload Is `ReaderSpreadFrame`

Decision: Flutter consumes a spread frame built by core. The app never rebuilds
spreads, page placement, display-list backgrounds, text targets, or resource
references.

Rito evidence:

- `buildSpreadDisplayList` already returns viewport-sized display lists:
  [`buildSpreadDisplayList`](../../packages/rito/src/reference/ts-core/render/display-list/spread-display-list.ts#L5-L27).
- Page background and clipping are display-list commands:
  [`appendPagePaint`](../../packages/rito/src/reference/ts-core/render/display-list/page-display-list.ts#L43-L56).
- Display-list code is tested as platform-neutral:
  [`display-list is platform-neutral`](../../packages/rito/tests/unit/architecture-invariants.test.ts#L117-L132).

External evidence:

- Readium's navigator owns display of resources and spread behavior:
  https://readium.org/architecture/navigator/.

Implementation rule: `ReaderSpreadFrame` contains display list, targets, text
runs, resource refs, viewport, page indexes, revision id, and a primary locator.
Flutter paints that payload full-viewport and routes gestures to its targets.

Acceptance:

- Double-page and single-page behavior matches Web because grouping is produced
  by core.
- Background colors are only painted from display-list commands or explicit
  transition states.
- Flutter code contains no app-side spread grouping logic.

### DR-3: Durable Position Is `ReaderLocator`

Decision: persisted reading state, bookmarks, annotations, search hits, and link
destinations use source locators. Page and spread indices are revision-local
cache values only.

Rito evidence:

- Current position persistence is still index-based:
  [`ReadingPosition`](../../packages/rito/src/reference/ts-core/interaction/position/model.ts#L4-L11).
- Existing navigation already resolves hrefs and anchors into revision-specific
  page/spread indices:
  [`findPageForTocEntry`](../../packages/rito/src/reference/ts-core/runtime/navigation.ts#L19-L48) and
  [`resolveTocEntryLocation`](../../packages/rito/src/reference/ts-core/runtime/navigation.ts#L62-L75).
- Hit maps already preserve source refs and source text offsets:
  [`textRunEntry`](../../packages/rito/src/reference/ts-core/interaction/core/hit-map.ts#L118-L138).

External evidence:

- Readium EPUB locator guidance requires href, type, and progression, and
  recommends total progression, position, and precise selector/range data:
  https://readium.org/architecture/models/locators/best-practices/format.html.

Implementation rule: the runtime resolves locators into spread frames for a
specific revision. Flutter can cache the resolved spread index, but persistence
must write the locator.

Acceptance:

- Resize, typography change, and spread-mode change keep the same logical
  reading position.
- Annotation geometry is recalculated per revision from locator data.
- No production persistence stores page index as the primary key.

### DR-4: Expensive Work Leaves the UI Isolate

Decision: EPUB parsing, CSS resolution, full or incremental layout,
display-list generation, search indexing, and resource decoding run in the
runtime path, not in Flutter widgets or painters.

Rito evidence:

- Core pagination is synchronous today:
  [`paginateNextChapter`](../../packages/rito/src/reference/ts-core/runtime/pagination-session.ts#L80-L123)
  and [`paginateAll`](../../packages/rito/src/reference/ts-core/runtime/pagination-session.ts#L126-L140).
- Images and fonts are already async platform capabilities:
  [`loadImagesWithDecoder`](../../packages/rito/src/reference/ts-core/render/assets/image-loader.ts#L5-L28)
  and
  [`loadFontsWithRegistry`](../../packages/rito/src/reference/ts-core/render/assets/font-loader.ts#L8-L47).

External evidence:

- Flutter isolates guidance ties isolate use to computations longer than the
  frame gap: https://docs.flutter.dev/perf/isolates.
- Flutter frame budget guidance sets the practical 16ms latency target:
  https://docs.flutter.dev/perf/best-practices.

Implementation rule: the controller may display the old frame while a pending
revision is computing, but it must not run layout work on the UI isolate.

Acceptance:

- Window resize does not block input.
- Reflow never displays page 1 as a fallback.
- The old frame remains active until the new target frame is ready or the
  controller intentionally disables interaction.

### DR-5: Text Measurement Is a Blocking Design Gate

Decision: native text measurement is not a convenience adapter. It is a
correctness and performance gate for the whole reader.

Rito evidence:

- Layout depends on `TextMeasurer`, not Canvas:
  [`TextMeasurer`](../../packages/rito/src/reference/ts-core/layout/text/text-measurer.ts#L26-L39).
- EPUB fonts must be loaded before pagination so measurement uses correct
  fonts:
  [`loadFontsWithRegistry`](../../packages/rito/src/reference/ts-core/render/assets/font-loader.ts#L8-L47).
- Hit testing uses measured text widths for character positions:
  [`resolveCharPosition`](../../packages/rito/src/reference/ts-core/interaction/core/hit-map.ts#L41-L62).

External evidence:

- Flutter exposes text rendering primitives through `dart:ui`:
  https://docs.flutter.dev/resources/architectural-overview.
- Flutter exposes runtime font loading:
  https://api.flutter.dev/flutter/services/FontLoader-class.html.

Implementation rule: before building product features on Flutter, prove one
measurement path that satisfies both visual parity and frame-budget
requirements. Candidate paths are a native/backend measurement engine, a
background-capable batched measurement service, or another measured platform
capability. A UI-isolate `TextPainter` loop can validate parity, but cannot be
accepted unless profiling proves it does not create jank for large EPUBs.

Acceptance:

- EPUB custom fonts, weights, styles, letter spacing, word spacing, line height,
  and writing mode assumptions match Web fixtures within documented tolerance.
- Measurement cache keys include the full structured paint input.
- Font registration completion is part of revision readiness.

### DR-6: Resource Payloads Are References

Decision: frames carry resource references, not repeated binary payloads.

Rito evidence:

- Current contracts already model image/font resources separately:
  [`ImageResource` and `FontResource`](../../packages/rito/src/reference/ts-core/render/assets/types.ts#L5-L21).
- Resource adapters are injected:
  [`ImageDecoder`](../../packages/rito/src/reference/ts-core/render/assets/types.ts#L10-L13) and
  [`FontRegistry`](../../packages/rito/src/reference/ts-core/render/assets/types.ts#L23-L25).

External evidence:

- Flutter isolates require object transfer between isolates; long-lived workers
  avoid repeated copy overhead:
  https://docs.flutter.dev/perf/isolates.

Implementation rule: binary bytes enter the runtime once per resource identity.
Frames reference cache keys. Flutter fetches resources through a resource API
and owns only its decoded presentation cache. The TypeScript runtime keeps
transfer ownership explicit: resource transfer records are scoped by
`sessionId` and `revisionId`, cancelled revisions release their records, and
session close/dispose clears all records for the session. Duplicate
revision/resource fetches may reuse a live transfer id, but the transfer store
retains lease counts so one consumer's release cannot invalidate another
consumer's payload.

Acceptance:

- No full-book base64 payload crosses the production app boundary.
- Resource transfer storage is bounded and session-scoped without evicting live
  payload leases.
- A frame can list pending resources explicitly without changing layout.

### DR-7: Render Backend Stays Pluggable

Decision: the first Flutter surface should consume display-list commands through
a `CustomPainter`, but the architecture must allow a future texture or native
backend behind the same frame contract.

Rito evidence:

- Render backend contracts are already abstract:
  [`DisplayListRenderer`](../../packages/rito/src/reference/ts-core/render/backends/types.ts#L4-L12).
- Architecture tests keep page/spread facades free of raw Canvas drawing:
  [`Canvas implementation lives in the Canvas backend`](../../packages/rito/tests/unit/architecture-invariants.test.ts#L146-L171).

External evidence:

- Flutter `Texture` can map backend-managed surfaces that repaint without
  executing Dart code:
  https://api.flutter.dev/flutter/widgets/Texture-class.html.

Implementation rule: do not bind `ReaderSpreadFrame` to Flutter widget internals.
The package renderer consumes the frame through an interface so `CustomPainter`
and future native texture backends share the same runtime contract.

Acceptance:

- Renderer tests can execute the same frame fixture through at least the Dart
  painter and a non-Flutter test renderer.
- No runtime API changes are required to replace the paint backend.

### DR-8: Web Goldens Are a Hard Gate

Decision: native work must not regress Web behavior. Any core/render change
touching layout, display list, hit maps, fonts, colors, images, or pagination
requires Web pixel verification.

Rito evidence:

- The existing pixel suite renders real EPUB bytes through the browser path:
  [`renderPixelRun`](../../packages/rito/tests/golden-pixel/golden-pixel.render.test.ts#L102-L138).
- Architecture invariants already enforce render/runtime boundaries:
  [`architecture-invariants.test.ts`](../../packages/rito/tests/unit/architecture-invariants.test.ts#L1-L15).

Implementation rule: native parity work must prefer adding contracts and tests
over modifying core behavior. If core behavior must change, update Web goldens
only after proving the change is intentional and correct.

Acceptance:

- Full Web golden pixel passes before any native-related core/render change is
  called done.
- Flutter frame fixture tests compare against core-generated frames, not
  hand-built approximations.

### DR-9: TypeScript Is the Implementation, the Protocol Is the Boundary

Decision: keep implementing Rito core in TypeScript, but define the reader
runtime boundary as a language-neutral protocol. Flutter must not depend on
JavaScript object identity, class instances, closures, DOM objects, Canvas
objects, or in-process promise chains.

Rito evidence:

- The published package is TypeScript/ESM today:
  [`package.json`](../../packages/rito/package.json#L1-L42).
- The existing render payload is already plain discriminated data:
  [`DisplayList`](../../packages/rito/src/reference/ts-core/render/display-list/types.ts#L14-L33).
- Backend integration is already expressed through structural contracts:
  [`DisplayListRenderer`](../../packages/rito/src/reference/ts-core/render/backends/types.ts#L4-L26).

Implementation rule: `ReaderRuntimeCommand`, `ReaderRuntimeResponse`,
`ReaderSpreadFrame`, `ReaderLocator`, `ReaderResourceRef`, and all request
objects must be wire-safe data. The protocol must define ids, revision
semantics, resource references, binary transfer ownership, error shapes, and
versioning without relying on TypeScript-only runtime behavior.

Acceptance:

- A non-TypeScript client can generate equivalent Dart/Swift/Kotlin/Rust models
  from the documented protocol without importing `@ritojs/core`.
- A test runtime can replay recorded command/response fixtures without executing
  the TypeScript implementation.
- Replacing the TypeScript implementation of a module with Rust/WASM/native code
  does not require changing the reader protocol.
- The Flutter package communicates with the runtime through protocol messages,
  not by reaching into TypeScript module internals.

Current core status: command/response fixture replay is covered at the
in-process transport, message-port transport, and worker-scope endpoint layers.

## Blocking Technical Spikes

These are not optional. They must complete before broad Flutter feature work,
because each one can invalidate the architecture if it fails.

### Spike A: Text Measurement Parity and Budget

Question: which native measurement capability can match Rito Web output without
blocking the UI isolate?

Evidence to collect:

- Compare Web display-list fixtures against native measured line breaks.
- Profile large EPUB layout on target desktop and mobile hardware.
- Verify custom EPUB font registration with runtime-loaded font bytes.

Exit rule: choose a measurement backend only after publishing fixture diffs,
timings, and cache-key design in this document or a linked implementation note.

### Spike B: Runtime Transport

Question: what transport gives typed, binary-safe, cancellable communication
between Flutter and the Rito runtime?

Evidence to collect:

- Measure EPUB open, revision creation, frame fetch, resource fetch, and cancel.
- Confirm background isolate/platform-channel constraints on each target
  platform.
- Prove stale revision responses cannot update controller state.

Exit rule: accept a transport only after it has tests for binary resources,
revision cancellation, stale responses, and structured errors.

### Spike C: Locator Mapping

Question: can Rito consistently map source locations to current revision
geometry for reading position, annotations, search, and selection?

Evidence to collect:

- Trace parser source refs through layout text runs into hit maps.
- Add fixtures for anchor navigation, plain text progression, and quoted
  annotation resolution.
- Verify resize and spread-mode changes preserve the same locator.

Exit rule: no app feature may persist page/spread index as the primary position
after this spike starts.

### Spike D: Cross-Backend Frame Parity

Question: can the same `ReaderSpreadFrame` drive Web Canvas and Flutter output
without app-side semantic reconstruction?

Evidence to collect:

- Produce fixed frame fixtures from core.
- Render them through the existing Web backend and Flutter painter.
- Compare colors, backgrounds, fonts, image bounds, link targets, and text
  target geometry.

Exit rule: if parity fails, fix the frame contract or backend implementation;
do not patch the app with special-case layout rules.

## Non-Negotiable Constraints

- Web Canvas behavior must not regress. Core/render changes require Web golden
  pixel verification before being considered correct.
- Layout remains the source of pagination truth. Flutter cannot implement a
  parallel paginator, spread grouper, style resolver, or hit-map resolver.
- The app must never block the UI isolate with EPUB parsing, CSS resolution,
  full-book layout, display-list construction, search indexing, or resource
  decoding.
- Resize and settings changes are revisioned. Old results cannot replace newer
  results, and partially computed revisions cannot become interactive.
- Reading position is source-based. Page index and spread index are ephemeral
  outputs of one layout revision.
- The reader surface is full-viewport. Any chrome is invoked by reader actions
  and must not change the core render area unless it intentionally requests a
  new layout revision.
- Embedded fonts, colors, page backgrounds, images, links, annotations, and
  text selection targets are part of the acceptance surface.

## Rejected Designs

### Whole-Book Export as Runtime Input

Rejected for production.

It couples unrelated concerns:

- metadata and TOC
- page display lists
- image/font byte payloads
- search text
- interaction targets
- current layout settings
- diagnostics serialization

It also creates poor performance characteristics:

- large JSON parse/serialize cost
- base64 memory amplification
- all-or-nothing reflow
- difficult cancellation
- high risk of stale first-page or stale-interaction bugs

This format may exist only as a diagnostic/export format with a name that makes
that status explicit, for example `ReaderDiagnosticExport`.

### Flutter Reconstructs Reader Semantics

Rejected.

Flutter must not build spreads from pages, derive search rectangles from paint
commands, infer image/link targets from draw commands, or synthesize page
backgrounds. Those are core/runtime responsibilities. Flutter owns painting,
gesture routing, menus, panels, persistence adapters, and platform file access.

### UI-Isolate Layout

Rejected for the production reader.

Flutter's main isolate is responsible for input, widgets, and frame production.
Any computation that misses the frame gap can create visible jank. EPUB parsing,
large JSON parsing, layout, search, and resource decoding all exceed that risk
profile. They must run in a worker/runtime path.

### WebView-Based Rendering

Rejected for this integration.

Rito's value is that it owns EPUB rendering without delegating DOM layout to a
browser. A WebView can be a separate product strategy, but it must not become
the native Rito rendering path.

## Accepted Architecture

```text
Flutter reader app
  -> rito_flutter package
       -> RitoReaderController
       -> ReaderSurface / overlays / persistence adapters
       -> ReaderRuntimeClient
            -> background runtime worker
                 -> bundled Rito core runtime
                 -> platform text measurement capability
                 -> resource cache
                 -> revision scheduler
                      -> @ritojs/core parser/style/layout/render/interaction
```

The native reader has three layers:

1. `@ritojs/core`
   Owns EPUB parsing, CSS resolution, layout, pagination, spread building,
   display-list generation, hit maps, locators, search indices, and annotation
   geometry resolution.

2. `rito_flutter`
   Owns typed Dart models, controller lifecycle, runtime messaging, frame
   caching, Flutter `CustomPainter` execution, overlays, reader actions, and
   platform persistence adapters.

3. `apps/flutter_reader`
   Owns product shell, file opening, app routing, menus, theming defaults, and
   platform packaging. The initial Flutter app scaffold now exists and consumes
   `rito_flutter`; file opening and platform runtime hosting remain separate
   app/native work.

## Core Runtime Model

### ReaderSession

`ReaderSession` is the authoritative runtime object for one opened publication.
It is not tied to Web Canvas or Flutter.

`openSession` returns the `ReaderPublication` summary in the protocol response.
The long-lived `ReaderSession` itself owns the loaded document and exposes only
revision-scoped runtime operations.

The session can internally use the existing `PaginationSession`, but the public
contract must be revisioned and asynchronous. Synchronous helpers can remain in
core for Web Canvas and tests, but they are not the native app boundary.
`createRevision` creates an observable `warming` revision before waiting on font
registration or pagination; cancellation keeps that revision observable as
`cancelled` and late async work must not overwrite it.

Resource bytes do not travel inside runtime control payloads. `getResource`
returns `ReaderResourcePayload` metadata only; the actual bytes must be stored
through a configured `StoreReaderResourceTransfer` side channel. Transfers are
tagged with `sessionId` and `revisionId` so cancel/close/dispose can release
side-channel bytes without guessing ownership. A session must fail resource
fetches when no transfer store is configured rather than emitting an unusable
transfer id.

### ReaderRevision

A revision is the result of one layout request:

```ts
interface ReaderRevision {
  readonly id: ReaderRevisionId;
  readonly sessionId: ReaderSessionId;
  readonly layoutKey: string;
  readonly status: 'warming' | 'ready' | 'complete' | 'cancelled' | 'failed';
  readonly knownSpreadCount: number;
  readonly finalSpreadCount?: number;
  readonly createdAt: number;
}
```

Every frame, search result, locator resolution, and resource response carries a
revision id. Flutter applies a response only when its revision matches the
active or pending revision it asked for.

### ReaderSpreadFrame

The frame is the only render payload the Flutter surface consumes:

```ts
interface ReaderSpreadFrame {
  readonly sessionId: ReaderSessionId;
  readonly revisionId: ReaderRevisionId;
  readonly spreadIndex: number;
  readonly pageIndexes: readonly number[];
  readonly viewport: { readonly width: number; readonly height: number };
  readonly displayList: DisplayList;
  readonly textRuns: readonly ReaderTextRunTarget[];
  readonly targets: readonly ReaderInteractionTarget[];
  readonly resourceRefs: readonly ReaderResourceRef[];
  readonly primaryLocator: ReaderLocator;
}
```

Important details:

- `displayList.width` and `displayList.height` match the logical viewport.
- The display list includes the complete background. Flutter must not paint its
  own page or spread background behind it except for transition effects.
- `targets` are already in spread coordinates.
- `textRuns` are already in spread coordinates.
- `resourceRefs` point to cached resources. Binary payloads are fetched through
  the resource API, not embedded into every frame.

### ReaderLocator

Reader position, bookmark, annotation, and search navigation must use source
locators:

```ts
interface ReaderLocator {
  readonly href: string;
  readonly mediaType: string;
  readonly progression: number;
  readonly totalProgression?: number;
  readonly position?: number;
  readonly anchorId?: string;
  readonly text?: {
    readonly before?: string;
    readonly highlight?: string;
    readonly after?: string;
  };
  readonly sourceRange?: {
    readonly start: number;
    readonly end: number;
  };
}
```

Page/spread index may be cached for one revision, but it is never persisted as
the primary reading position.

### ReaderInteractionTarget

Interactions are semantic, not inferred from paint:

```ts
interface ReaderInteractionTarget {
  readonly kind: 'link' | 'image' | 'footnote' | 'text';
  readonly rect: Rect;
  readonly locator: ReaderLocator;
  readonly href?: string;
  readonly footnoteRef?: ReaderFootnoteRef;
  readonly resourceRef?: ReaderResourceRef;
  readonly label: string;
}
```

Flutter receives the target and decides which UI to show. It does not inspect
draw commands to decide whether something is a link or image.

## Flutter Runtime Architecture

### Package Split

The Flutter implementation should be split into a reusable package and the app:

```text
packages/rito_flutter/
  lib/
    src/controller/
    src/runtime/
    src/render/
    src/ui/
    src/persistence/
  pigeon/
  test/

apps/flutter_reader/
  lib/
  integration_test/
```

The app consumes `rito_flutter`. Shared reader logic must not live only inside
the app.

### Runtime Worker

The runtime worker is long-lived and owns the Rito core runtime for one or more
sessions. It runs outside the UI isolate.

Required properties:

- command/response protocol is typed and versioned
- EPUB bytes move as binary data, not base64 text
- resources move by reference and cache key
- responses include `sessionId`, `revisionId`, and request id
- cancellation is explicit
- stale responses are ignored by the controller
- worker errors are structured

The current app-local JavaScript call pattern is not a production boundary. The
runtime bundle can still be generated from `@ritojs/core`, but it must be owned
by the Flutter package build and hidden behind `ReaderRuntimeClient`.

### Text Measurement

Text measurement is the hardest part of native parity.

Production requirements:

- measurement and painting must use equivalent font families, weights, styles,
  letter spacing, word spacing, line height, and writing-mode assumptions
- layout must not synchronously call the UI isolate for every text run
- font registration must finish before a revision that depends on those fonts is
  accepted
- custom EPUB fonts must be available to both measurement and painting

`TextPainter` on the UI isolate can validate correctness, but it cannot be the
accepted production measurement path for full-book pagination if it creates
jank. The accepted path is a runtime text measurement capability that can run
off the UI isolate or a batched scheduler proven by frame-budget tests. If the
measurement backend cannot meet those tests, the Flutter reader is not done.

### Resource Management

Resources are session-scoped:

- fonts: extracted, registered, and keyed by family/src/weight/style/hash
- images: decoded asynchronously, cached by resource ref, evicted by LRU
- CSS/image dimensions: resolved before layout when needed
- binary payloads: never embedded in every frame

The render surface can request an image ref and paint a placeholder only when
the frame explicitly marks that resource as pending. The placeholder is a
resource loading state, not a layout fallback.

### UI and Reflow Flow

Resize/settings changes follow this sequence:

1. Capture the current `ReaderLocator`.
2. Mark a pending revision and keep the current frame visible.
3. Apply visual transition to the old frame if desired.
4. Request a new revision from the runtime.
5. Resolve the locator in the new revision.
6. Request the target spread frame.
7. Atomically swap active revision + frame + controller position.
8. Start prefetch for adjacent frames.

The UI never shows page 1 as a fallback during reflow. If a new revision is not
ready, the old revision remains active and interactive state is either retained
or intentionally disabled by the controller.

## Interaction Architecture

### Navigation

Navigation commands target locators or runtime-resolved spread indices:

- next/previous spread
- TOC href
- link href
- search result locator
- bookmark locator
- annotation locator

Only the runtime resolves these into revision-specific spread indices.

### Search

Search is source-index based. The runtime returns:

- locator
- snippet
- optional current-revision rects if available

The Flutter UI can show results immediately from source text and request frame
rects lazily for visible results.

### Annotations

Persistent annotations store locator + quote + user payload. They do not store
only page index and rect.

At render time, the runtime resolves annotation locators into current-revision
rects. This keeps annotations stable across font changes, resize, spread mode,
and line-breaking changes.

Current internal runtime support resolves source-range locators into
revision-scoped spread-coordinate geometry segments. Text-only locators and
page/spread fallback locators deliberately return `not-supported` for geometry
so callers cannot accidentally persist coarse page rectangles as annotation
anchors.

### Images and Links

Image and link taps come from `ReaderInteractionTarget`. The target identifies
the resource or href directly. Flutter opens a lightbox, modal, or external
handler without inspecting display-list commands.

### Footnotes

Footnote taps are link hit-map entries promoted to `kind: 'footnote'` only when
the runtime can resolve the noteref href to a known `footnoteMap` key. Same-page
`#id` refs are resolved through the current page's chapter range, while
cross-document refs resolve through manifest href metadata. The frame carries a
small `ReaderFootnoteRef`; `getFootnote` fetches the structured `FootnoteEntry`
through a revision-scoped command.

## Performance Strategy

### Frame Budget

The reader targets:

- no synchronous work on the UI isolate that can exceed one frame gap
- render surface repaint under the practical Flutter frame budget
- no all-book JSON parse on the UI isolate
- no base64 resource expansion in the app layer

### Caching

The runtime maintains:

- parsed publication cache
- stylesheet/style cache
- font metric cache
- image dimension cache
- revision cache
- spread frame cache around the current locator
- source search index cache

The Flutter package maintains:

- decoded image cache
- current/previous/next frame cache
- overlay geometry cache keyed by revision/frame
- user preference and locator persistence

### Prefetch

After each active frame change:

- prefetch previous and next spread frames
- prefetch image resources referenced by those frames
- keep a small bounded cache
- cancel prefetch for stale revisions

This follows the navigator principle that nearby resources can be prepared
before the user reaches them.

Current core status: `prefetch` is wired through the internal command protocol
and warms revision-scoped spread frames into a frame cache keyed by spread index
and display-list options. It also best-effort warms image resources referenced by
those frames through the session's side-channel transfer store, reusing live
transfer records by revision/resource identity. It does not yet run a background
scheduling queue; that remains worker/resource-pipeline work.

Current core search status: `search` is wired through the internal command
protocol, client, dispatcher, and session layers. It searches the
revision-scoped chapter text indices and returns source-range locators with
text context. `resolveLocator` can resolve those source-range locators back to
the current revision's page/spread by using hit maps; text-only locator
fallback remains explicitly unsupported.
