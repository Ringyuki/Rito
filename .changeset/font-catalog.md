Fonts resolve the way CSS resolves them against installed fonts, and paint draws exactly the face that shaped each run. A named family is the publication's `@font-face` family of that name, else the host face of that name; a generic (`serif`, `sans-serif`, `monospace`, `system-ui`) is the host faces of its role, language-neutral faces first, then those tagged for a language with the content's own `lang` ahead of the rest; every host face follows as the fallback, serif first. Shaping runs under the content language, so `locl` applies as in the browser. Every text, ruby and marker run now names one face by its alias (a run shaped across faces paints once per face), publication faces register under a per-file alias with their `@font-face` weight and style, and pinned faces report their own weight and slope, so the platform synthesizes bold or italic exactly where CSS would. Artifacts list the pinned faces they paint with (`rito-host-font:<sha256>` hrefs, readable through `readResource`), so a reader-session host registers every face it needs from the artifact alone. New: `reader.fonts()` / `session.fonts()` return the font catalog (host and publication families with role, language and faces) to build font choices from; `addFontFaces` and `removeFontFaces` change the host faces while a book is open (a system font, an imported file) and lay it out again; `unresolvedFontFamilies` names what a `font-family` list would skip, and the kit controller reports such names from `setTypography` as an `error` event with source `font-family`. The same operations exist on the Flutter session (`fontCatalog`, `addFontFaces`, `removeFontFaces`, `unresolvedFontFamilies`) and the C ABI (`rito_font_catalog`, `rito_unresolved_font_families`, `rito_add_host_font_faces`, `rito_remove_host_font_faces`).
